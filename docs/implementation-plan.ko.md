# 구현 계획 — Solo Raid 우선

작성: 2026-09-08. 상태: **P00·P01·P02 구현 완료 / 히트 정수화 실측 판정 대기 / P03 5인 스킬 효과 실행 연결**. [P03 스킬 구현 범위·출처](p03-skill-runtime.ko.md), [P01 검증 보고서](p01-verification.ko.md)와 [P01 기능 출처](p01-source-map.ko.md)에 현재 지원 범위·검증 결과를 기록했다. 실제 팀 게이지·보스 기믹·실게임 수치 재대조·성능 검증은 후속 단계다.

계산·제품 설계는 [architecture-draft.ko.md](C:/Users/user/Documents/GitHub/Nikke-Simul/docs/architecture-draft.ko.md)를 따른다. 이 문서는 그 설계를 실제 작업 순서와 완료 조건으로 구체화한다. 여기의 P00~P09는 설계 문서의 개략 단계보다 세분화한 실행 단위다.

## 1. 고정 기준과 범위

- 작업 위치: Nikke-Simul. 기존 Nikke-Dmg-Simulator는 이식 원본·검증 자료로 사용한다.
- 차지: 기본 × (1 + 배율 증가분 합) + 가산 합. 기존 C# 해당 식은 이식본에서 수정한다.
- 기초 스탯: 실게임 오차 0으로 검증된 C# 구현을 채택하고 계산 순서·정수화를 보존한다.
- 히트 정수화: 후보식 비교가 필요하다. 비교용 정책을 분리하고 판정 전 결과는 provisional로 구분한다.
- 버스트: 실제 팀 게이지 누적과 단계별 사이클을 완성한다.
- 초기 UI: nikke-calc 재사용. C# 정밀 엔진, Python fetch/ETL·대조, 로컬 API·SQLite, CPU worker를 기본으로 한다.
- 1차 대상: Solo Raid 보스 1종과 여러 후보 덱. 주요 5덱을 구성할 수 있는 검증된 로스터까지 순차 확대한다.
- 정적 보스는 개발용 fixture다. 실제 추천에는 해당 보스의 명중 가능 구간·파츠·기믹 및 필요한 생존 조건을 반영한다.

첫 보스·캐릭터 범위는 P01에서 가용 스펙·관측 자료와 효과 지원 범위를 확인해 정한다. 아직 특정 시즌이나 캐릭터를 지원 확정으로 선언하지 않는다. 선택에 필요한 정보가 부족해도 공통 코어·입력 규격·검산 도구는 먼저 진행할 수 있다.

## 2. 전체 실행 순서

```text
P00 원본 고정·개발 기반
  → P01 데이터 계약·스펙 정규화·검증 범위
  → P02 C# 스탯·차지 이식 및 히트 정수화 비교
  → P03 무기·스킬·효과별 기록
  → P04 실제 팀 게이지·버스트 사이클
  → P05 보스·택틱·단일 덱 실전 대조·웹 연결 완성
  → P06 영속 기록·CPU 반복 실행·통계·retry
  → P07 후보 탐색·비중복 5덱 최적화
  → P08 부위별 오버로드 육성 추천
  → P09 Union Raid·성능 확장
```

UI 입력과 API 골격은 P01부터 준비하고, 모든 단계가 같은 결과 규격을 사용한다. P02~P04의 임시 결과도 검산 화면에서 볼 수 있게 한다. P01에서 SQLite 계정 snapshot·동기화 이력 저장을 구현한다. 전투 표본 저장은 P05까지 1회 결과를 연결하고, P06에서 대량 실행 가능한 운영 기능으로 확장한다.

히트 정수화 판정을 기다리는 동안 fetch·UI·스킬·팀 상태 구현은 계속할 수 있다. 다만 비교용 정책별 결과를 분리하며, 미확정 상태의 임시 표본을 검증된 추천 데이터와 합치지 않는다. 성능보다 정확성 확인이 선행한다.

## 3. 제안 프로젝트 구조

```text
apps/web/                  upstream UI와 backend adapter
src/Nikke.Core/            검증된 스탯·수치 연산·히트 대미지
src/Nikke.Engine/          시간·무기·스킬·팀·보스 전투 상태
src/Nikke.Contracts/       요청·결과·snapshot 경계 DTO
src/Nikke.Data/            DTO → 엔진 입력 변환, snapshot 읽기
src/Nikke.Storage/         SQLite schema·migration·batch writer
src/Nikke.Analysis/        통계·retry·후보 선별·육성 평가
src/Nikke.Jobs/            작업 상태·CPU worker·체크포인트
src/Nikke.Api/             웹 API와 애플리케이션 조립
tools/data-pipeline/       fetch·ETL
tools/reference/           버전 고정 upstream Python 대조 실행
tests/                     이식·계산·전투·통계·통합 검증
docs/                      결정·지원 범위·검산·벤치 기록
data/local/                개인 스펙·원천 데이터·로컬 DB (gitignore)
```

이는 목표 모듈 구분이다. P00에서 빈 프로젝트를 전부 생성하지 않고 실제 기능을 구현하는 단계에 필요한 것만 만든다. Engine → Core 의존을 유지하며 UI·DB·fetch가 엔진 내부로 들어가지 않도록 한다. 계약 DTO와 직렬화는 바깥 adapter에서 변환한다. 초기에는 한 로컬 API 프로세스에 모듈을 조립해 운영할 수 있다.

## 5. P01 — 버튼 기반 계정 스펙 동기화

상세 설계: [P01 동기화 설계](p01-sync-design.ko.md). 기본 흐름은 **내 스펙 동기화 버튼 → 백엔드 수집·정제·검증·저장**이다. 최초 연결/세션 만료 때 로그인하며 CSV는 후순위다. 아래 P01-1~P01-6은 구현했으며 실제 193명 수집·저장 필드 대조를 확인했다. 한계는 검증 보고서에 기록했다.

구현 순서:

1. **P01-1 계약·fixture:** AccountConnection/SyncJob/RawManifest/GameSnapshot/AccountSnapshot/CharacterBuild/EquipmentLine/ManualOverride 계약을 정한다. 원천 ID, 4부위×3줄, 옵션 ID·수치·단위·등급·잠금, unknown과 출처를 보존한다. 전투 계약은 snapshot 참조 경계부터 정한다.
2. **P01-2 정제·검증:** C# adapter가 원천 JSON을 공통 snapshot으로 변환한다. 정상·누락·중복·미지원 fixture로 값 보존과 판정을 검증한다. 개발용 fixture는 사용자 CSV 제출 요구가 아니다.
3. **P01-3 저장·작업 API:** SQLite에 작업 이력·snapshot·current 포인터를 구현한다. 검증과 파일 저장 완료 후 transaction으로 current를 전환한다. 취소·중복 클릭·재시작·실패 시 정상 스펙을 보존한다.
4. **P01-4 실제 수집:** 기존 getFromBlaLink.py의 브라우저 세션/배치 수집을 연결하고, upstream HTTP 수집·전초기지 호출 구조를 참고해 반복 갱신을 구현한다. 최초 로그인 및 서버·계정 선택, 만료 재연결을 제공한다.
5. **P01-5 UI:** 연결·동기화 버튼, 진행 단계·수집 수·변경 내역·누락 안내·장비 상세·수동 보완을 연결한다. 정제 규칙은 백엔드에서 통일하고 기존 UI 계산기 기본값으로 미확인 스펙을 채우지 않는다.
6. **P01-6 대조·인계:** 실제 원천 및 가능한 실게임 화면과 저장 필드를 대조하고 출처·수정 내역을 기록한다. 첫 보스·최소 덱 후보와 5덱 후보군의 effect 지원 범위를 정리한다.

완료 조건: 정상 세션에서 버튼 한 번으로 수집·검증·저장·결과 확인이 끝난다. 상세 누락이나 계정 불일치는 current 전환을 막고, 선택 정보 미확인은 unknown으로 보존한다. 장비 부위·줄·옵션이 저장 후에도 유지되고, 같은 snapshot으로 동일한 전투 입력을 구성할 수 있다. 새 동기화는 진행 중 전투가 고정한 snapshot에 영향을 주지 않는다.

확인 화면: 동기화 진행·완료·재로그인·실패 상태, 캐릭터별 스펙·장비 줄·누락/변경 내역과 수동 보완. CSV 입력·대미지 계산 완성·대량 worker는 P01 필수 범위에 포함하지 않는다.

## 6. P02 — 계산 코어와 히트 검산

구현 완료. [검증 결과](p02-verification.ko.md)와 [기능별 출처](p02-source-map.ko.md)를 기록했다. 사용자의 후속 지시에 따라 히트 정수화의 최종 판정은 추후 실측 대조 대상으로 유지한다. 계산 화면과 비교 도구는 사용할 수 있다.

구현 순서:

1. C# StatCalculator·OverloadProcessor와 필요한 테이블 접근을 이식한다. 원본의 검증 fixture로 단계별 스탯이 일치하는지 확인한다.
2. 차지식을 확정식으로 수정한다. 기본·가산만·배율만·동시 적용·비차지 조건을 검증한다.
3. HitContext와 DamageBreakdown을 정의한다. 계수·공방차·차지·거리·풀버스트·크리·코어·유형별 버프의 값과 정수화 위치를 반환한다.
4. 동일 입력에 대한 C# 항별 floor 경로와 upstream 최종 round 경로의 비교 하네스를 만든다. 차지·기초 스탯 차이는 제거하고 정수화만 비교한다.
5. 기존 실측점·원천 계수 및 후보가 갈리는 경계 입력을 비교표로 출력한다. 실게임 측정이 없는 synthetic 입력은 구현 차이를 보여주는 자료이며 정답의 증거로 사용하지 않는다.
6. 근거가 충분한 범위를 판정하고, 부족한 범위는 어떤 입력·관측이 필요한지 구체적으로 남긴다.

검증 기준: 이식 전후 기초 스탯 일치, 확정 차지식 일치, 대미지 유형별 적용 조건 확인. 정수화 후보 선택 시 허용오차를 느슨하게 바꿔 억지로 통과시키지 않는다. 실제 계수의 정밀도 한계를 명시한다.

확인 화면/산출물: 기본 UI는 최종 HP·공격력·방어력 세 값, 선택해서 여는 단일 히트 검산과 후보별 실게임 잔차표. 중간 스탯·계산항은 API/JSON에 보존한다. OL·스킬 공증은 같은 스탯 원값으로 합산하며 [P02 정정 기록](p02-buff-correction.ko.md)의 회귀 기준을 따른다.

## 7. P03 — 무기·스킬 런타임과 효과별 기록

세부 순서:

1. 프레임 시계, 발사/명중/탄 소비/재장전 이벤트, 같은 프레임의 안정된 처리 순서를 연결한다.
2. 기존 FiringModel을 이식하고 대표 무기별 발수·차지·재장전·MG ramp·SG 펠릿을 검증한다.
3. 상시 버프와 타격/횟수/시간 트리거, 조건, 대상 선택, 스택/갱신/만료를 연결한다.
4. 직접 스킬 대미지·추가타·DoT·분배·탄약/쿨다운/게이지 효과를 구현한다.
5. ChangeWeapon·InstantSkill body, 연결 효과, 소환·애장품 교체·스탯 변환을 첫 후보군의 필요 순서대로 구현한다.
6. canCrit/canCore, 계수 기준 스탯, 스냅샷 시점, 대상·파츠 조건을 damage instance별로 지정한다.
7. 발사 원인 → 스킬 → effect → 후속 대미지의 ID와 인과 관계를 최종 결과까지 보존한다.
8. 동일 실행 경로에 summary sink와 trace sink를 붙인다. 상세 로그를 꺼도 전투 동작과 집계 의미가 달라지지 않아야 한다.

완료 조건: 선정한 단일 캐릭터/소규모 팀에서 발사·스킬 발동·스택·버프 uptime을 설명할 수 있다. 팀 총합 = 구성원 합계 = 중복 없는 직접 대미지 effect 합계가 성립한다. 미지원 effect/조건/대상은 지원표와 결과 진단에 나타난다.

이 단계에서 등록 캐릭터 수를 늘리기 위해 미지원 효과를 생략한 결과를 완전 지원으로 표시하지 않는다. P04에 필요한 쿨다운·게이지·버스트 이벤트 인터페이스를 먼저 준비한다.

## 8. P04 — 팀 게이지·버스트 사이클 완성

세부 순서:

1. TeamState에 공용 게이지·현재 단계·시전자·풀버스트 상태를 둔다. 개인 쿨다운은 캐릭터 상태에서 관리한다.
2. 어떤 발사/명중/관통/펠릿/스킬 이벤트가 얼마의 게이지를 생성하는지 원천 규칙을 적용한다. 게이지 증가 원인을 기록한다.
3. 충전 → I → II → III → 풀버스트 → 종료 → 재충전의 기본 루프를 구현한다.
4. 버스트 사용 가능 조건·시전자 우선순위·대기/대체·쿨다운 시작/감소·사용자 조작 지연을 연결한다.
5. 단계 재진입·여러 단계 사용·풀버스트 연장/단축 등 대상 후보군의 특수 동작을 적용한다.
6. 무기 변경/탄약/버프와 버스트가 서로 갱신하는 순서를 검증한다. 버스트 스킬 발동과 풀버스트 진입은 별개 이벤트로 남긴다.
7. 이전의 고정 충전시간 및 단순 쿨타임 시전 경로를 정밀 실행에서 제거한다. 비교 도구에서 사용한다면 모델을 명시해 격리한다.

완료 조건: 5인 180초 전투에서 외부 충전시간 입력 없이 여러 사이클이 동작한다. 실제 첫 버스트·이후 진입 시점·풀버스트 횟수/유지시간과 대조한다. 장탄/차속/쿨감 변경이 게이지와 사이클에 미치는 효과를 설명할 수 있다. 사용 가능한 단계가 없는 상태도 정의된 정책으로 처리한다.

확인 화면: 시간별 게이지, 단계별 시전자, 쿨다운, 풀버스트 구간, 그 구간의 딜 분해.

## 9. P05 — 보스·택틱·단일 덱 제품 연결

구현:

1. 보스 1종의 몸체·코어·파츠 HP, 파괴·재생, 무적/이동 구간, 거리·명중 모델, 필수 기믹을 연결한다.
2. 관통·범위 타격의 대상 수와 파츠 파괴가 이후 타격/스킬/게이지에 미치는 영향을 구현한다.
3. 수동 조작 대상·엄폐·차지 유지/톡톡이·버스트 시퀀스를 TacticSpec으로 실행한다.
4. 해당 덱·보스에 필요한 피격·회복·HP 조건·전투불능을 구현한다. 생존을 생략한 개발용 시나리오는 조건부 결과로 구분한다.
5. nikke-calc UI의 계산 호출을 BackendClient로 분리하고 입력 → snapshot → C# 1회 실행 → 결과 표시를 연결한다.
6. 1회 결과와 snapshot 참조를 SQLite에 저장하고 다시 조회한다. UI 기본 스펙이 누락된 계정 스펙을 덮어쓰지 않도록 한다.
7. 전체 대미지만이 아니라 스탯·발수·크리·버스트·효과 발동·파츠 타이밍을 원본 전투 관측과 비교한다.
8. 확정 스펙과 동일한 택틱으로 여러 관측/실행을 비교해 확률 변동과 모델 누락을 분리한다.

완료 조건: 내 스펙으로 1덱을 실행하고 저장된 평타·스킬·effect별 결과와 타임라인을 다시 볼 수 있다. 정밀 지원을 선언한 보스/덱에 핵심 미지원 동작이 없다. 모든 판에서 완전히 같은 대미지를 요구하지 않고, 통제 가능한 중간 관측과 확률 범위를 함께 검증한다.

이 단계가 첫 실사용 마일스톤이다. 단일 덱 검증에 통과한 범위부터 다음 단계의 정식 표본 대상으로 승격한다.

## 10. P06 — 표본 저장·CPU 배치·통계·retry

구현 순서:

1. P05의 run/run_member/run_effect 저장을 batch·experiment·버전 필터와 연결한다. 같은 run ID 재전송으로 중복 표본이 생기지 않도록 한다.
2. 작업 생성/진행률/취소/재개, 상태 전이, batch 완료 체크포인트를 구현한다. 중단된 미완료 run은 표본에서 제외하고 새 실행으로 보충한다.
3. run 단위 CPU 병렬 실행을 구현한다. 실행 상태와 RNG는 run별로 격리하고 기존 고정 시드 금지 원칙을 유지한다.
4. bounded queue + 단일 batch writer로 기록한다. DB 쓰기 지연이 메모리를 무한 증가시키지 않게 한다.
5. 평균·표본 표준편차·분위수·컷 초과확률·신뢰구간을 계산한다. 평균 CI와 한 판 결과 범위, N과 리트 예산 n을 구별한다.
6. pilot에서 분산/처리량을 측정하고 최종 검증 N을 결정한다. 적응적 탐색용 표본과 최종 평가 표본을 구분한다.
7. retry 성공확률, 평균 시도/시간, 정해진 n에서 기대 최고점을 계산한다. 전투시간·재진입시간·조기 포기 정책을 입력으로 둔다.
8. 대표 완성 덱에서 run/s, 코어별 확장성, 메모리, DB 크기, 기록 비용을 측정하고 병목을 개선한다.

완료 조건: 중단·재개·중복 전송 이후에도 유효 표본 수와 집계가 정확하다. 분석 가능한 간단한 분포 fixture에서 확률/통계/리트식이 맞고, 독립 배치의 차이가 예상 불확실성과 부합한다. 미지원/실패 run과 정상 0 대미지를 구분한다.

확인 화면: 덱별 누적 N, 분포 그래프, 목표 컷 성공확률·CI, 리트 시간, 계산 작업 진행률.

## 11. P07 — Solo Raid 비중복 5덱

1차: 검증된 후보 덱 목록을 입력받는 selector부터 구현한다. 정확히 5덱, 캐릭터별 사용 최대 1회, 해당 규칙에 따른 큐브 제약을 적용한다. 평균 또는 고정 리트 예산 기대 최고점 합계를 목적값으로 둔다.

2차: 로스터에서 후보를 생성한다. 버스트 유효성·시너지·프리셋에 교체/교환/무작위 탐색을 추가하고, 이미 있는 snapshot/덱/택틱 결과를 캐시한다. 개인 대미지만 낮다는 이유로 지원 캐릭터 후보를 제거하지 않는다.

3차: 후보 생성 → 소규모 표본 → 조합 선별 → 경쟁 조합의 불확실한 덱 추가 표본의 반복을 연결한다. 최종 후보 조합은 독립 표본으로 확인한다. 탈락 후보 중 일부도 재탐색해 초기 오차에 의한 영구 배제를 줄인다.

4차: 전체 시간 예산에 따른 덱별 리트 배분과 합산 컷 확률을 확장한다. 덱별 분위수의 단순 합을 합산 분위수로 표시하지 않는다.

완료 조건: 작은 후보 풀에서는 완전탐색 결과와 일치하고, 큰 후보 풀에서는 후보 수·검색 범위·solver gap·표본 오차를 보고한다. 선택 결과의 캐릭터 비중복이 성립하며 미지원 캐릭터를 쓰지 않는다. 후보 풀 내부 최적과 전체 로스터 전역 최적을 구별한다.

확인 화면: 추천 5덱, 목적값과 CI, 대체 조합, 리트 예산, 각 후보의 지원 상태.

## 12. P08 — 오버로드 육성 추천

P08-A: 고정 변경의 가치 평가

- 특정 캐릭터/장비/줄의 옵션·수치를 사용자가 지정하면 변경 전후를 평가한다.
- 우선 덱 고정으로 계산하고, 유망 변경은 후보 덱 재평가 및 5덱 재선별까지 수행한다.
- 본인 딜, 해당 덱, 5덱 합계, 버스트/장탄/차지 임계점 영향을 보여준다.
- 전후 개선량의 불확실성을 추정한다. 통계 오차보다 작은 차이를 명확한 우열로 표시하지 않는다.

P08-B: 다음 한 번의 행동 추천

- 현행 옵션·줄·수치·중복 제한·잠금·결과 유지/교체 규칙과 비용을 공식 근거/원천 자료로 확인하고 버전 고정한다.
- 장비 상태에서 가능한 행동별 결과 확률과 비용을 계산한다.
- 기대 5덱 목적값 증가/모듈, 개선 확률, 임계 도달확률을 기준으로 부위별 행동을 추천한다.
- 규칙·확률표가 확보되지 않았다면 P08-A는 제공하고 기대 소모량·확률 기반 순위는 미확정으로 둔다.

P08-C: 예산별 육성 경로

- 옵션 확보 → 잠금 → 수치 재설정의 순차 정책을 평가한다.
- 예산 내 기대 성능·목표 달성확률·기대 비용·중단 시점을 제공한다.
- 스탯 근사로 후보 행동을 줄이고 유망 결과에 정밀 MC를 사용한다. 임계점에서는 반드시 정밀 재평가한다.

완료 조건: 실제 장비 상태로 실행 가능한 행동만 제안하고, 잠금·결과 선택·비용·확률이 일관된다. 작은 상태 공간의 열거 결과와 정책 평가가 일치한다. OL 변경 결과의 RNG와 전투 RNG를 분리해 해석한다.

확인 화면: 캐릭터/부위/행동/잠금/기대 합산 개선/모듈 효율/신뢰구간 및 예산별 경로.

## 13. P09 — 후속 확장

- Union Raid: 3덱 선별, 보스 진행·잔여 HP·오버킬·실제 사용 제한을 추가한다.
- GPU: CPU 프로파일상 필요한 경우에만 같은 조건 batch 또는 특정 계산부터 실험한다. 전송·변환을 포함한 전체 시간과 수치/분포 동등성을 비교한다.
- 원격 서비스·멀티호스트: 실제 수요와 로컬 처리량을 기준으로 작업 큐·저장소·인증을 확장한다.
- 지원 범위: 신규 보스·캐릭터·효과는 같은 검증 절차로 추가한다. 데이터만 존재하는 상태와 구현/실전 검증 완료를 구별한다.

이 확장들은 Solo Raid 결과의 정확성이나 5덱·육성 기능의 선행조건이 아니다.

## 14. 첫 착수 묶음과 결과 보고 방식

첫 착수는 P00~P02의 다음 다섯 결과물에 집중한다.

1. 원본 commit/hash·라이선스·기준 테스트 결과.
2. 장비 줄을 보존하는 입력/결과 schema와 샘플 fixture.
3. C# 스탯 이식 및 원본과의 동일성 보고.
4. 확정 차지식 구현과 네 조건 회귀 결과.
5. 단일 히트 정수화 후보 비교표와 추가 관측이 필요한 조건.

그 뒤 P03~P05에서 사용자가 직접 확인할 수 있는 단일 덱 경로를 완성한다. 각 작업 묶음은 변경 범위·검증 결과·미지원 범위·다음 작업을 함께 기록한다. 지원 범위 밖 결과로 추천 순위를 확정하지 않는다.

달력 일정은 지금 확정하지 않는다. 핵심 비용은 미지원 effect와 보스 기믹의 범위에 달려 있다. P01의 지원표와 P02의 이식 결과가 나온 뒤 P03~P05의 작업량을 다시 산정하고, P06의 실제 처리량으로 대량 표본 수집 시간을 산정한다.
