## 2. `defenceRatioRate` = 방어율 (사용자 확인)

- 공식 명칭 **방어율**. 최근 생긴 보스 기믹으로, **최종 대미지에서 일정 비율을 감소**시킨다.
- **true damage(방어 무시) 니케는 방어율을 무시**한다. 예: 최종 대미지 10, 방어율 60% → 일반 4, true damage 10.
- 구현 반영: 클라이언트 공식의 `(1 − defenceRatioRate)` 항을 true damage 타입에서는 1로 둔다. 보스별 값은 보스 StaticData에서 가져온다(아래 4절).

## 3. 실게임 1-tick 대조 준비 (사용자 도구 준비 완료)

사용자가 더미 보스로 속성을 정하고 1-tick 대미지를 대조하는 도구를 준비했다.

### 3-1. "114 or 115" 질문의 의미

공격력 조립 `Attack = statAtk + Σ round(statAtk × atkBuff × buffNum)`에서 **기본값 100, 버프 14.5% 1개일 때 버프분이 14.5 → 15(사사오입)인지 14인지**를 묻는 것이다. 곱셈을 정확한 값이나 float32로 하면 14.5 → 15(공격력 115), double로 하면 14.499999999999998 → 14(공격력 114). 버프 비율이 x.5로 떨어지는 조합을 골라 1-tick으로 확인하면 판정된다.

### 3-2. SW 버스트 20억 초과 타격 관측 분석

사용자 관측: 조합 츠바이(애장품)·민트·스노우 화이트·맥스웰·수헬름(헬름 아쿠아 마린). SW OL 우월 코드 29.46% × 4, 크리 대미지 합 79.48%, 파츠 대미지 큐브. 한 방 4타 [몸통, 파츠, 파츠, 파츠+코어]:

| 판정 | 대미지 |
|---|---:|
| 몸통 | 492,046,946 |
| 파츠 | 543,020,538 (2타) |
| 파츠 + 코어 | 738,858,011 |
| 합 | 2,316,946,033 |

Director 분석:

1. **방어력은 이 세 값만으로 역산할 수 없다.** 세 타격은 같은 공격력·방어력·계수를 공유하므로 비율을 잡으면 `(attack − defence) × …` 항이 소거된다. 방어력을 풀려면 그 순간의 최종 공격력이 필요하거나, **공격력을 알려진 양만큼 바꾼 두 1-tick의 차이**가 필요하다(D ∝ A − DEF이므로 A를 Δ만큼 바꾸면 A − DEF = Δ·D₁/(D₂ − D₁)). 1-tick 도구로 이 실험을 권장한다.
2. 비율로 얻는 것: 파츠/몸통 = 1.10359(파츠 항이 extra에 주는 증가분), 파츠+코어/파츠 = 1.36064(B에 코어가 더해지는 비율). 크리 79.48% + 기본 크리 50% + 풀버스트 50%만으로 B(코어 없음) = 2.7948로 두면 코어 증가분이 1.0079로 나와 일반 코어 +100%에 가깝지만 정확히 1이 아니다. 다른 크리·코어 버프(민트·맥스웰 등)가 빠졌을 가능성이 크다 — 버프 목록이 확정되면 다시 계산한다.
3. **중요 — float32 최종 곱 가설과 충돌.** 세 값 모두 **float32로 표현할 수 없는 정수**다(이 크기에서 float32 간격은 32~64인데 738,858,011은 홀수, 나머지도 32의 배수가 아님). 현재 `client_f32`는 최종 곱까지 float32에 저장한 뒤 반올림하므로 이 크기의 피해는 32~64의 배수로만 나온다. 따라서 **최종 곱(또는 적어도 마지막 단계)은 float32가 아닌 정밀도(double 등)로 계산된다**는 강한 근거다. 클라이언트 공식의 B는 float32 누적이라는 정보와 함께 보면, 앞서 비교한 후보 중 "**B는 float32, 곱셈 사슬은 double**"(①)이 유력하다. 단, 표시값이 여러 부분 피해의 정수 합이라면 이 논리가 약해지므로 1-tick 도구의 단일 인스턴스로 확인한다.
   - 다음 실험: 1-tick 관측값이 float32 표현 가능한지(2^24 이상 큰 타격), 그리고 ①/② 후보 중 어느 쪽과 일치하는지 대조. 엔진에 ① 후보 정책을 비교용으로 추가하는 작업이 필요하다.
4. 방어력 전환: 4타 합이 20억을 넘지만 두 파츠 타격이 같은 값이고 그 뒤 타격이 없어, 이 한 방 안에서의 전환 여부는 판정할 수 없다.

## 4. 데이터 출처 (사용자 제공)

- **보스 데이터:** StaticData에 있다. 다만 보스가 앞뒤로 움직이는 등 동적 패턴이 많으므로 **행동 트리·보스 함수·타임라인과 그에 따른 거리 변화는 사용자가 별도로 제공**한다.
- **OL 확률 테이블:** StaticData(웹 검색으로도 확인 가능)에서 확보한다. **최근 패치 규칙: 같은 옵션 + 같은 수치는 다시 나오지 않는다.**
  - 효과 변경: 예) 2·3줄 잠금, 1줄 [방어력 증가 11.11%] → 변경 결과로 [방어력 증가 9.00%]는 가능(수치가 다름). 내부적으로 [방어력 증가 11.11%]가 다시 나오면 재추첨한다(반복 가능, 추가 비용 없음).
  - 수치 재설정: 옵션 고정, 수치만 바뀌며 현재 수치(11.11%)는 제외하고 나온다 — 같은 옵션·같은 수치면 내부적으로 한 번 더 시행.
  - 확률 모델: 현재 (옵션, 수치)를 제외한 조건부 분포로 다시 정규화한 것과 같다.

## 5. `statDamageRatio` 조사 상태

H-SRC(2026-09-28) 결론: **원천 데이터만으로 결론 불가.** 스킬 계수는 CharacterSkill·Function 테이블에 있고, 별도로 `MonsterStatEnhanceTable.level_statdamageratio`(몬스터 공격자 스탯 배율 후보)가 있어 공식의 어느 변수인지 확정하지 못했다. 니케 → 보스 공격에 보스 행 값을 넣을 근거는 없어 기본 1을 쓴다. 확정 방법은 두 가지다: (a) 클라이언트 코드에서 대입 경로 확인(사용자 환경), (b) 1-tick 실험 — 스킬 계수를 알고 있는 타격이 `statDamageRatio = 1`로 모델과 일치하면 니케 공격에서는 중립으로 판정. **(b)는 사용자 도구로 가능하므로 별도 환경이 꼭 필요하지는 않다.**
